# Mode: 产品评测

**触发信号:**
- 用户提到"评测一下 XX"、"试用 XX"、"用了 XX 怎么样"
- 用户给出产品官网链接 + 想分享体验
- 用户问"XX 和 YY 哪个好"(对比型评测,可参考结构 H)

**推荐结构:** A(介绍型,深度评测) 或 H(对比测评)

**推荐长度:** 3000-4500 字(单产品),3500-5000 字(对比型)

---

## 研究流程

### Step 1:产品官网 + 文档(必做)

```
web_fetch(产品官网)
web_fetch(产品文档站)
```

提取:
- 产品定位 / 一句话描述
- 主打功能
- 定价模式
- 目标用户
- 上线时间

### Step 2:用户真实评价(必做!)

**官网说的不算,真实用户怎么说才算。**

```
web_search("产品名 评测 真实使用")
web_search("产品名 vs 竞品 对比")
web_search("产品名 缺点 问题")  ← 重要!
```

要找:
- ✅ 中肯的评价(不是软文)
- ✅ 用户在 Twitter/X / Reddit / 知乎的吐槽
- ✅ 第三方独立评测
- ❌ 避开纯粹的官方软文

### Step 3:同类竞品(对比型评测必做)

```
web_search("产品名 alternative")
web_search("XX 类型 工具 对比")
```

了解市场上的竞品全貌。

### Step 4:作者亲自体验(理想情况)

如果是给用户写他自己的体验,要:
- 让用户描述他的真实感受
- 提取他的具体使用场景
- 问他踩过的坑

## 写作要点

### 1. 必须有缺点

**没有缺点的评测是软文**。读者一眼就能识别。

每个产品都有问题:
- 慢、贵、复杂、不稳定
- 缺某个核心功能
- 学习曲线陡
- 定价模式有坑

**至少 2-4 个真实痛点**。

### 2. 具体场景胜过抽象描述

❌ "这个产品很好用"
✅ "我用它处理一个 5000 行的代码库重构,只花了 30 分钟,而手动至少要 2 小时"

数字 + 场景 = 可信。

### 3. 区分付费功能和免费功能

定价模式要写清楚:
- 哪些是免费的
- 哪些要付费
- 付费分几档
- 是否有学生 / 创业者优惠

### 4. 公平对比

如果做对比测评:
- 不要"我家最好"那种偏向
- 列出每个产品的优劣势
- 给出"在 X 场景下选 A,在 Y 场景下选 B"的建议

### 5. 避免商业利益冲突嫌疑

如果你和这个产品有商业关系(被赞助、是 affiliate),**必须披露**。

如果只是个人使用感受,也可以注明:
> "本评测无商业合作,基于个人付费使用 3 个月的体验"

### 6. 标题模式建议

- 强观点(决定换回旧工具):**模式 11(观点宣言型)**
- 反差(花了大钱但...):**模式 7(反差悬念型)**
- 数字佐证(用了 X 个月):**模式 1(数据震撼型)**
- 疑问钩子:**模式 8(疑问钩子型)**

## 已知陷阱

### 陷阱 1:写软文不自知

如果通篇都是赞美,没有一个缺点 → **就是软文**。
读者不傻,会立刻识别并取消关注。

### 陷阱 2:用旧版本评测

产品迭代快。如果你是 3 个月前的体验:
- 可能某些痛点已经被修复了
- 可能新增了重要功能
- 写之前要确认你说的"问题"现在还存在

### 陷阱 3:基于"道听途说"评测

"我朋友说这个产品不好用..."→ 这不是你的评测。
**只写自己实际用过的东西**,或如实标注信息来源。

### 陷阱 4:刻意平衡 vs 真实判断

不要为了"显得公平"而强行说一些不痛不痒的好话。
- 如果产品真的很差,如实写
- 如果产品真的很好,也如实写
- **真实的偏向 > 假的平衡**

### 陷阱 5:推荐了不在用的产品

写推荐文章时,要确认产品**当前还在维护、还能用**。
- 看官网最近一次更新
- 看公司是否还活着
- 看用户最近的反馈
