# Mode: 教程指南

**触发信号:**
- 用户提到"教程"、"怎么做"、"how-to"、"保姆级"
- 用户希望"手把手"教读者做某件事
- 内容是"步骤型"的(Step 1, Step 2...)

**推荐结构:** E(教程型)

**推荐长度:** 3000-5000 字

---

## 研究流程

### Step 1:确认操作可行性(必做!)

**绝对禁止凭印象写教程**。每一步都必须可重现。

- 用户给的链接/文档:`web_fetch` 看完整内容
- 第三方教程:`web_search` 找最新教程
- 官方文档:**永远以官方文档为准**

### Step 2:核实最新版本

教程类内容**最容易过时**。
- 软件版本号
- API 是否变化
- UI 是否改版
- 政策是否调整

```
web_search("产品名 最新版本")
web_search("产品名 2026 教程")  ← 加年份过滤老内容
```

### Step 3:踩坑收集

读者最讨厌"按教程做但卡住了"。
要主动收集:
- 常见错误信息
- 常见配置问题
- 兼容性问题(操作系统、版本)

```
web_search("产品名 安装 报错")
web_search("产品名 常见问题")
```

### Step 4:验证流程完整性

每一步之间**不能有跳跃**。
- 用户从哪个状态开始?
- 每一步做完后,应该看到什么?
- 怎么验证这一步成功了?

## 写作要点

### 1. 命令必须可复制粘贴

不要伪代码、不要"大概是这样":
- 完整命令
- 用代码块包裹
- 如果有占位符,用 `<your-name>` 等显眼标记

### 2. 每步都要有预期

读者需要知道"我做对了吗"。
- 每步执行后应该看到什么
- 命令的输出应该长什么样
- 失败时会显示什么错误

### 3. 截图(可选)

公众号支持插图,但 markdown 文件本身没有图。
可以在文中标注:
> [此处建议截图:配置页面的最终状态]

让用户后续手动加图。

### 4. 操作系统兼容性

如果命令在不同 OS 不同:
- 分别写 Mac / Windows / Linux 的版本
- 标注清楚
- 不要假定读者是 Mac 用户

### 5. 版本号要写对

API、SDK、软件版本变化快。
- 写明你测试的版本
- 提示读者:"如果使用更新版本可能略有差异"

### 6. 提供"故障排查"

教程跑不通是最大的痛点。
- 收集 3-5 个最常见的错误
- 给出明确的解决方案
- 提供"还是不行?"的兜底建议

### 7. 标题模式建议

- 数字承诺(N 分钟搞定):**模式 9(福利紧迫型)**
- 痛点解决(月费 $20 vs 免费):**模式 2(对比落差型)**
- 渴望直白:**模式 5(身份共鸣型)**

## 已知陷阱

### 陷阱 1:跳步

资深作者经常跳过他们觉得"显然"的步骤,但对新手来说不显然。
- 假设读者是**初学者**
- 不省任何"显而易见"的步骤
- 包括"打开终端"这种基础操作

### 陷阱 2:过时教程

教程文章生命周期短。
- 写明"截至 2026 年 4 月"
- 提供"如果 UI 变了,去哪找最新教程"的兜底
- 重要更新发生时,要重写教程

### 陷阱 3:单平台教程

只写 Mac 版,Windows 用户用不了 → 流量损失一半。
**至少考虑:**
- Mac
- Windows(WSL or 原生)
- Linux(Ubuntu 为主)

### 陷阱 4:命令直接粘贴有问题

直接从 ChatGPT / 别人博客复制的命令可能:
- 用了 smart quote(全角引号)而非半角
- 多了 `\` 行尾续行符
- 路径用了别人的用户名

**全部测试一遍**才能放进文章。

### 陷阱 5:忘了 cleanup

教程跑完后,读者可能想清理。
- 怎么卸载?
- 怎么重置?
- 怎么删除产生的文件?

可选的"卸载/清理"节会给读者安全感。
