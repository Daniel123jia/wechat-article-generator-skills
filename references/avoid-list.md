# 写作雷区清单

写作过程中必须避免的 18 种常见错误。

---

## 雷区 1:编造信息

### 错误做法
没看原始素材、没搜索、纯靠"印象"写。

### 后果
写错数据、错记功能、把"计划中"说成"已有"——读者一查就尴尬。

### 正确做法
**所有事实都必须经过 web_fetch 或 web_search 验证**。不确定的信息,要么查证要么不写,**绝不"补全"**。

---

## 雷区 2:翻译腔严重

### 反面
> 这是一个伟大的、令人惊叹的工具,它让你能够轻松地实现各种各样的功能。

### 正面
> 简单好用的工具,它把那些原本要你折腾半天的事,做成了一个命令搞定。

### 检查
读出来。如果听着像"AI 翻译的维基百科",就要重写。

---

## 雷区 3:过度营销

### 红词清单(必须避免)
- 震惊 / 逆天 / 碾压 / 秒杀
- 王炸 / 神级(慎用)/ 颠覆
- 屠榜 / 万能 / 完美 / 终极
- 革命性 / 划时代

### 正面替代
| 红词 | 替代 |
| :--- | :--- |
| 震惊 | "让人惊喜的是" |
| 逆天 | "出乎意料地好" |
| 碾压 | "表现优于" |
| 颠覆 | "打破了之前的常规" |
| 革命性 | "带来了真正的变化" |

---

## 雷区 4:堆砌式描述

### 反面
> 该项目支持多种语言,包括 Python、Java、JavaScript、TypeScript、Go、Rust、C、C++、PHP、Ruby、Swift、Kotlin、Scala、Haskell 等数十种语言。

### 正面
> 几乎覆盖所有主流语言——Python、JS、Go、Rust 应有尽有。如果你日常用的语言不在里面才奇怪。

**信息密度比信息数量重要**。

---

## 雷区 5:无脑加 emoji

### 反面
> 🚀🔥💯 这个项目真的太棒了!✨⭐💎 大家一定要去试试!🎉🎊🎁

### 正面
> 这个项目值得每个 Java 开发者认真试一下。

### 规则
- emoji 用于**功能小节标题**
- emoji 用于**信息表格**
- emoji **不用于正文段落**(除特殊语境)

---

## 雷区 6:鸡汤式收尾

### 反面
> 让我们一起拥抱开源,共建技术美好未来!愿你也能在技术道路上越走越远!

### 正面
> 8 年时间,8000+ Star,无数企业在生产环境中使用——这份成绩,值得每一个 Java 开发者认真看一看。

### 规则
- 不要"未来已来"、"乘风破浪"、"一起加油"等空话
- 用具体的、和素材相关的反思收束
- 数据 + 事实 > 情绪渲染

---

## 雷区 7:多素材合并到一个文件

### 错误做法
用户给了 5 个素材,你生成了一个`合集.md`包含所有 5 个。

### 后果
公众号是单篇发布,合集没法用。

### 正确做法
**永远是 N 个素材 → N 个独立 .md 文件**。

---

## 雷区 8:不读原素材直接写

### 错误做法
看到项目名是 "AingDesk",根据名字猜测是个桌面 AI 工具,然后开写。

### 后果
基本特性都搞错。

### 正确做法
**第一步永远是抓原素材**(web_fetch)。

---

## 雷区 9:中英标点混用

### 反面
> 这个项目获得了8.1k Star, 是一个非常优秀的项目, 适合所有Java开发者使用.

### 正面
> 这个项目获得了 8.1k Star,是一个非常优秀的项目,适合所有 Java 开发者使用。

### 规则
- 用中文标点(,。;:?!""''——……)
- 中英文之间有空格
- 标点不要重复("!!!" → "!")

---

## 雷区 10:复读机式赞美

### 反面
> 这个项目非常优秀。
> 这个项目非常出色。
> 这个项目非常牛逼。

### 后果
读者看完什么也没记住。

### 正确做法
每段都要有**新信息**。

---

## 雷区 11:忽视用户的明确指令

### 用户原话
> "分别帮我生成"、"独立成文"、"复制一次即可"、"不要放在一起"

### 错误理解
"在一个文件里放多个,用分隔符分开"。

### 正确做法
**严格按字面意思**:N 个 → N 个独立文件。

---

## 雷区 12:写过长的文章

### 问题
公众号读者平均阅读 2-4 分钟。一篇 6000+ 字读者根本读不完。

### 正确长度
- **理想:2500-4500 中文字符**
- **极限:不超过 5500 字**

如果素材太丰富,**做减法**——只保留最关键的,而不是堆砌全部。

---

## 雷区 13:Cargo Cult Tech Term(术语堆砌)

### 错误做法
为了显得专业,堆砌读者不一定理解的术语:

> "基于 Transformer 架构的多模态预训练大模型,采用 RLHF 进行对齐,支持 MoE 稀疏激活和 KV Cache 优化"

### 正确做法
术语**为传达信息服务**,不为炫耀服务:

> "用了主流的 Transformer 架构,经过 RLHF 对齐——简单说就是,不会胡说八道"

---

## 雷区 14:断章取义

### 错误做法
只看 README 第一段或新闻摘要,就开写。

### 正确做法
至少要看完原素材的:
- 主体内容(README / 新闻全文 / 论文 abstract+intro)
- 核心论点
- 时效性(发布日期 / 最近更新)
- 关键数据

---

## 雷区 15:忽略时间线

### 错误做法
写文章时不关注素材的时间。

### 后果
- 项目半年前就停止维护了,你写得像它"正在活跃开发"
- 新闻是 3 个月前的,你写得像今天发生的
- 论文已经被新研究反驳了,你还在介绍

### 正确做法
每写一篇都要看:
- 原始素材的发布日期
- 是否还在维护/有效
- 是否有更新版本

如果素材已经过时,要么不写,要么如实说明时效。

---

## 雷区 16:标题党 - 内容货不对板

### 错误做法
标题写"震惊!XX 公司倒闭了"实际是"XX 业务调整"。

### 后果
读者打开后觉得被骗,**取消关注**。

### 正确做法
标题可以**抓眼球**,但**不能撒谎**。如果用了"颠覆""碾压"等词,文章主体必须能支撑这个判断。

---

## 雷区 17:正确的废话

### 反面
> 这是一个非常优秀的项目,值得每个开发者去使用,它能帮助你提升效率。

这段话**包含 0 信息**。

### 正面
> 项目最大的优势是 BYOK 模式——用你自己的 API Key,不用付订阅费,Token 用多少花多少。

每句话都要回答:**它具体解决了什么 / 怎么做到的 / 数据是多少**。

---

## 雷区 18:政治/意识形态/敏感话题

### 必须避免
- 政治倾向明显的表达
- 涉及国家/民族/宗教的判断
- 名人的私生活议论
- 未经核实的指控

### 安全做法
- 描述事实,不下道德判断
- 引用多方观点,而非自己当裁判
- 涉及敏感话题时,**点到即止**或**直接绕开**
- 政治、宗教、医疗、法律——**都需要特别谨慎**

---

## 自检清单(写完后过一遍)

### 真实性
- [ ] 所有数据都验证过(没编造)
- [ ] 素材时效性确认(还有效吗)
- [ ] 不涉及未核实的指控

### 表达
- [ ] 没有翻译腔
- [ ] 没用红词("震惊/逆天/碾压"等)
- [ ] 中英文之间有空格
- [ ] 标点全部中文标点
- [ ] emoji 只用在小节标题和表格
- [ ] 加粗用得克制

### 内容
- [ ] 没有正确的废话
- [ ] 每段都有新信息
- [ ] 收尾不鸡汤
- [ ] 标题不党

### 输出
- [ ] 每个素材独立文件
- [ ] 长度在推荐范围
- [ ] 文件名格式正确
- [ ] 保存到正确目录

### 安全
- [ ] 不涉及敏感政治话题
- [ ] 不涉及未核实的人身攻击
- [ ] 不涉及违法/违规内容

通过自检的文章,才能交付。
