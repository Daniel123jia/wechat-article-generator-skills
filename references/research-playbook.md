# 研究取材方法论

每种素材类型有不同的研究路径。这个文档是**通用的研究指引**,各 mode 文件会有针对性的细化。

---

## 总原则

### 1. 素材真实性 > 写作速度

宁可多研究 5 分钟,不可写错信息。

### 2. 多源交叉验证

单一来源容易出错。重要事实**至少 2 个来源**确认。

### 3. 时效优先

引用最新信息。新闻/数据要看发布日期,过时的不要用。

### 4. 中文资料优先于英文翻译

如果有现成中文报道,引用中文。除非英文原文本身就是关键(如官方公告、论文摘要)。

---

## 核心工具

### web_fetch

抓取**指定 URL** 的页面内容。

**适合:**
- 用户给了具体链接(GitHub repo / arXiv 论文 / 新闻链接 / 推特)
- 要看一个页面的完整内容
- 官方信息源(公司官网、官方博客)

**用法示例:**
```
web_fetch("https://github.com/owner/repo")
web_fetch("https://arxiv.org/abs/2401.12345")
web_fetch("https://example.com/news/article-id")
```

**限制:**
- 有些页面有反爬虫(GitHub 通常 OK,推特/X 不一定)
- 私有/付费页面无法访问
- 重型 JavaScript 渲染的页面可能拿不到完整内容

---

### web_search

通用网络搜索,返回多个结果。

**适合:**
- 不知道具体 URL,只有关键词
- 找补充信息、第三方评论、中文报道
- 搜索趋势、最近动态、市场反馈

**用法策略:**

#### 查询长度
- 最佳:**3-6 个关键词**
- 太长(10+ 词)→ 召回率下降
- 太短(1-2 词)→ 噪声大

#### 查询质量

**好的查询:**
```
"Cline VS Code MCP plan act mode"
"GLM-4.7 性能 评测 中文"
"NVIDIA NIM 免费 API 申请教程"
```

**差的查询:**
```
"这个项目怎么样"  ← 太模糊
"我想知道关于 Cline 的所有信息"  ← 太啰嗦
```

#### 多轮搜索策略

**第一轮:** 项目名 + 核心特征
**第二轮:** 项目名 + 中文评测/教程
**第三轮:** 项目名 + 具体功能/对比

---

### image_search(谨慎使用)

公众号文章是**纯文字 markdown**,通常**不需要插图**。

**只在以下情况用:**
- 用户明确要求"加图"
- 教程类文章必须图示某个关键步骤

**不用的情况:**
- 普通介绍文(用 markdown 表格代替)
- 正常的文章节奏(emoji 已经够了)

## 信息查证清单

不同类型素材必须确认的关键信息:

### 共通必查
- [ ] 主体名称(公司/项目/作者/事件)的正确拼写
- [ ] 关键日期(发布/创建/最近更新)
- [ ] 关键数据(数字/规模)
- [ ] 关键论点(主张/承诺/价值)

### GitHub 项目额外
- [ ] Star / Fork 数(实时,不能用旧数据)
- [ ] License
- [ ] 主要语言/技术栈
- [ ] 最近一次 commit 时间
- [ ] 当前最新 release 版本

### 新闻事件额外
- [ ] 事件发生时间
- [ ] 涉及方(公司/人物)
- [ ] 关键数字(融资额/用户数/损失等)
- [ ] 官方表态

### 学术论文额外
- [ ] arXiv ID 或 DOI
- [ ] 作者所属机构
- [ ] 发表年份
- [ ] 是否已被同行评议(预印本 vs 正式发表)

### 推特帖子额外
- [ ] 发帖人身份核实
- [ ] 发帖时间
- [ ] 互动数(转发/点赞)
- [ ] 帖子原文(完整)

### 福利/产品额外
- [ ] 政策有效期
- [ ] 适用范围(国家/地区)
- [ ] 是否需要付费
- [ ] 是否有时间限制

## 来源可信度判断

### A 级(高可信)
- 官方公告(公司官网、官方博客)
- 学术论文(arXiv、Nature、ICLR、ACL 等)
- GitHub README(项目作者维护)
- 主流媒体(Reuters、彭博、Wall Street Journal 等)
- 知名科技媒体(TechCrunch、The Verge 等)

### B 级(中可信)
- 知名个人博客(本人就是该领域专家)
- 大型中文科技媒体(36 氪、虎嗅、量子位等)
- 知乎专栏文章(高赞、作者认证)
- 微信公众号(认证、有专业背景)

### C 级(低可信,需交叉验证)
- 营销号、转载号
- 匿名发帖
- 二手翻译稿(失真风险)
- AI 生成的文章(可能编造)

### 引用规则
- A 级来源:可直接引用,标注来源
- B 级来源:可引用,但要交叉验证
- C 级来源:**不可作为唯一来源**

## 研究深度判断

根据素材热度和复杂度调整:

### 知名素材(主流话题)
- ✅ 用 1-2 个 web_fetch 抓主要来源
- ✅ 1 次 web_search 找中文报道
- ⚠️ 可省深度对比

### 中等素材
- ✅ 2-3 次 web_fetch
- ✅ 2-3 次 web_search
- ✅ 找作者背景
- ✅ 找同类对比

### 冷门/复杂素材
- 全部 4 个工具都用
- 可能要 5+ 次搜索才能凑齐信息
- 实在搜不到,**诚实说明信息有限**,不要编造

## "搜不到怎么办?"

### 第一步:换关键词

- 中文搜不到 → 试英文
- 英文搜不到 → 试中文
- 全名搜不到 → 试简称或别名
- 加修饰词 → 加领域、时间、地点等

### 第二步:找上下文

如果直接信息缺失,可以查相邻信息:
- 项目所属公司 → 查公司其他动态
- 论文作者 → 查作者其他论文
- 事件主角 → 查相关方表态

### 第三步:坦诚处理

如果实在搜不到,有 3 种正确做法:

**做法 A:文章中如实说明**
> "项目还很早期,公开信息有限。以下基于 README 整理。"

**做法 B:省略相关章节**
不要为了凑字数而编造。该删的就删。

**做法 C:建议用户换素材**
"这个素材目前公开信息太少,可能不适合写公众号。建议换一个,或等等再写。"

**永远不要编造来填补空缺。**

## 信息整理模板

研究完毕后,按这个模板整理(写文章前):

```
## 素材:{名称}

### 基础事实
- 类型:
- 主体:
- 关键日期:
- 来源(主):
- 来源(次):

### 核心数据
- 数据 1:[具体数字 + 来源]
- 数据 2:[具体数字 + 来源]

### 关键人物/机构
- ...

### 核心论点/特性(3-7 个)
1. ...
2. ...

### 时效性
- 是否还有效:
- 有效期/截止日期:

### 痛点钩子素材
- 读者最熟悉的、与本素材相关的痛点:

### 标题候选(3 个)
1. [模式]:...
2. [模式]:...
3. [模式]:...

### 结构选择
[A-I 中的哪一种]
```

模板填好后,再开始写文章。

## 常见研究陷阱

### 陷阱 1:把"自己说的"当事实

公司发的新闻稿、项目自己的 README 都有美化倾向。
**对策:** 找第三方报道交叉验证。

### 陷阱 2:把旧数据当新数据

GitHub Star 数变化快,3 个月前的报道里的数字现在可能翻倍了。
**对策:** 关键数据用最新来源。

### 陷阱 3:只看英文不看中文

英文圈和中文圈的关注点常常不同。中文用户的痛点可能在英文报道里完全没有。
**对策:** 中英文资料都看。

### 陷阱 4:把 AI 生成内容当真

很多内容农场用 AI 批量生产文章,事实经常错。
**对策:** 偏 C 级来源,需要 A/B 级交叉验证。
